# 三专家（code / tool / general）数据分工与 SFT 甜点量

> 本文回答三个问题：MiniMind 为什么这么分工、`sft_t2t.jsonl` 到底是什么、
> 三个专家各自该用多少 SFT 数据、这些数据能不能直接从现有语料里抽。
> 结论全部基于本地实测（`minimind/dataset/*.jsonl`），没有下载任何外部数据。
>
> 配套文档：`doc/data_plan_145m.md`（数据源与筛选口径）、`doc/moe_specialization.md`（专家分化）。

---

## 1. MiniMind 的实际数据分工（实测）

### 1.1 预训练：几乎只有"中文通用文本"

`minimind/dataset/pretrain_t2t.jsonl`（8.28 GB，约 2.2B token），抽样 3 万条：

| 类别 | 文档占比 | 说明 |
|---|---|---|
| general | 96.1% | 中文合成指令/问答文风（"给定一段文本…好的，请再…"） |
| code | 2.1% | 是**"教你怎么写代码"的对话**，不是源码 |
| math | 1.8% | 解题对话 |
| **tool** | **0.0%** | 一条都没有 |

按位置采样还能看到一个事实：**数据是按来源成块拼接的**，不是打散的。
第 58% 附近有一段 code 占比 15.2% 的块，其余位置只有 0.1–2.9%。

### 1.2 SFT：工具调用被塞在文件末尾一整块

`sft_t2t_mini.jsonl`（1.74 GB，**905,718 条**）：

| 位置 | 内容 |
|---|---|
| 0–8% | 99% 通用 |
| 16% | 32.5% 代码（一个代码块） |
| 25–58% | 通用 82–88% + 代码 9–14% |
| 66–83% | 96–100% 通用 |
| **91–100%（第 771,075–905,718 行）** | **100% tool-call，134,644 条（14.9%）** |

`sft_t2t.jsonl`（14.10 GB，约 **857 万条**，平均 1644 B/条）：

| 位置 | 内容 |
|---|---|
| 0–33% | 通用 70–79%、代码 17–28% |
| 41%、58%、66% | 通用 92–98% |
| 75% | 数学 22.8%（一个数学块） |
| **83%** | **代码 72.6%（一个大代码块）** |
| 91% | 通用 95% |
| 尾部 | tool 块（与 mini 同构） |

**结论**：MiniMind 的分工是

```text
预训练  = 中文通用文本（几乎不含 tool，代码极少）
SFT     = 通用 + 代码 + 数学 + 末尾 13.5 万条 tool-call
RL      = rlaif（通用）/ agent_rl（tool/agent）
```

## 2. 为什么 tool 不进预训练、code 只放 2%

**不是"场景太简单所以不用学"，而是技能性质不同。**

| 技能 | 性质 | 该在哪学 | 原因 |
|---|---|---|---|
| 世界知识 / 语言 | 分布 | 预训练 | 需要海量、多样、长尾 |
| 写代码 | 分布（有语法/语义规律） | 预训练少量 + SFT 主要 | 需要见过真实源码，但 145M 容量有限 |
| 工具调用 | **格式 + 策略** | SFT 学格式、RL 学策略 | schema 高度重复、信息密度低，预训练 ROI 极差 |

tool 不进预训练的四个具体理由：

1. **格式技能不需要分布覆盖**：几千条 SFT 就能让模型学会 `system.tools → tool_calls → tool 结果 → 回答` 这个模式；
2. **token 成本极高**：schema 是嵌套 JSON，6400 词表下极贵，同样 1M token 放 tool 远不如放中文长文；
3. **过触发风险**：预训练里塞满 `<tool_call>`，模型会在闲聊时也吐工具调用，SFT 要花力气纠偏；
4. **信息密度低**：`{"name": "calculate_math", "arguments": {...}}` 的重复率极高，对语言建模几乎没有增益。

code 只放 2% 则更多是**工程现实**：

- 他们的语料来自中文指令/蒸馏数据（MiniMind README 写明来源是匠数、Magpie 等），本身没有代码仓库管线；
- 6400 词表下 Python 是 0.426 tok/byte，中文是 0.245——**同样 token 预算，放代码少看 1.7 倍字节**；
- 145M 的容量是硬约束，每个领域都在抢参数。

至于"代码加多了会不会伤语言"：**10–15% 的代码通常有益**（提升结构化推理与格式遵循），
到 25–30% 以上才开始明显挤占自然语言能力。判断标准是预训练后 C-Eval/CMMLU + 中文 PPL
相对纯通用基线掉不超过 1–2 个点。

## 3. 三个专家的 SFT 甜点量

### 3.1 总量从哪来

SFT 预算 = `steps × batch_tokens × grad_accum`（`batch_tokens` 是全局 micro-batch，
一个 optimizer step 要跑 `grad_accum` 次）。当前 `configs/sft/*.yaml` 是
8,192 × 16 = **131,072 input token / step**，三个专家分别 210 / 100 / 80 步。

2026-11-11 重建数据后实测（seed=1234，全量扫描 + 去重 + 随机抽样）：

| 专家 | 抽样条数 | input token | target token | 步数 | target epoch |
|---|---:|---:|---:|---:|---:|
| general | 50,000 | 25.59M | 21.63M | 210 | ≈1.0 |
| code | 30,000 | 12.31M | 5.69M | 100 | ≈1.0 |
| tool | 8,000 | 5.41M | 1.93M | 80 | ≈1.8 |

旧的 500×32,768×8=131M/专家 是早期草稿，和现在的 145M 配置不一致；旧的
“取文件前 N 条”预算（general 120 / code 90 / tool 80）实际只有
0.59 / 0.94 / 1.84 epoch。**SFT 超过 1–2 epoch 就是浪费**；
`scripts/sft_step_budget.py` 可以在数据/混料变化后重新算。

### 3.2 甜点表

| 专家 | SFT 条数 | token | epoch | 为什么是这个量 |
|---|---|---|---|---|
| **general** | 40–60k | 15–20M | 1 | 多样性无界（知识/风格/安全/多语言），永远喂不满；但 145M 容量封顶，60k 之后边际收益快速下降 |
| **code** | 25–35k | 12M | 1 | **不是"好学"，是容量受限**：能吸收的代码空间就那么大，再堆只增加过拟合 |
| **tool** | 5–10k | 4–6M | 2–3 | 窄格式技能，**少而重复**优于多而杂；多了会过触发、对固定 schema 过拟合 |

比例约 **4 : 2 : 1**（general : code : tool），不是按数据集大小对齐。

### 3.3 一个反直觉点

- **tool 数据要"少而重复"**：同一批 schema 多跑 2–3 epoch，比换 10 万条新 schema 更有效，
  因为要学的是"看到 schema 就按格式调用"这个不变的模式；
- **code 数据要"多而多样"**：要的是不同函数签名、不同边界条件、不同报错场景，
  而不是同一道题的多份解法；
- **general 数据要"广而干净"**：宁要 40k 条高质量，不要 400k 条含代码/数学/tool 混杂的记录。

## 4. 能不能直接从现有 SFT 里提取

**能，但三个领域的可用程度差很多。**

| 专家 | 能否提取 | 实测可用量 | 判断 |
|---|---|---|---|
| **general** | ✅ 可以 | `sft_t2t.jsonl` 中约 72.4% × 857 万 ≈ **620 万条**，过滤后仍有百万级 | 直接抽 40–60k，但要先剔掉代码/数学/tool |
| **tool** | ✅ 已有 | `sft_t2t_mini` 尾部 **134,644 条**（已抽成 `data/sft_tool.jsonl`） | 直接可用，抽 5–10k |
| **code** | ⚠️ 只能起步 | 约 18% × 857 万 ≈ **154 万条含代码块**，但抽样看质量很杂 | 需强过滤；覆盖不到"可执行代码"这一档 |

### 4.1 general 的提取规则

不要按行号截取——**数据是按来源成块拼接的**（tool 在末尾、code 在 83%、math 在 75%），
按位置采样会整块吃进或整块错过。要按内容过滤：

```python
drop if "```" in record          # 代码块
drop if "\\frac" / "\\boxed" / "解方程" in record   # 数学
drop if message.get("tools") or message.get("tool_calls")   # tool
drop if len(turns) < 2 or empty assistant
```

### 4.2 code 的提取规则与局限

抽样 83% 位置（代码块最密集处）看到的实际内容：

- ✅ 一部分是真正的 Python 函数题（英文，"implement a function that..."）；
- ⚠️ 一部分是 CSS/前端问答、架构设计描述、甚至"准确率公式"这种误判；
- ❌ 几乎没有带测试、可执行验证的样本。

所以提取时必须：

1. 代码块内必须 `ast.parse` 通过且含 `def`；
2. 只留 Python（丢 CSS/JS/SQL）；
3. ≤60 行、只用标准库；
4. 去重（同一题多版本很常见）。

按这个口径能从 154 万条里留下大约 **10–30 万条**，足够做 SFT 起步集，
但**覆盖不到"函数签名 + 单元测试"这一档**，所以 code GRPO 仍然需要外部数据（MBPP/open-r1/TACO）。

### 4.3 一句话

```text
general：现成，抽 40–60k（过滤后）
tool   ：现成，抽 5–10k（尾部 13.5 万条里选）
code   ：能抽出 10–30k 的"问答式代码"，够 SFT 起步；
         但 GRPO 要的"带测试的题"必须外补
```

## 5. 预训练配比（3B，不再锁 1.2B）

对 145M（61M 激活），**3B token 是甜点**，5B 以上边际收益很低。

| 组 | token | 占比 | 来源 |
|---|---|---|---|
| 中文通用 | 1.2B | 40% | 现有 MiniMind pretrain |
| 英文教育 | 450M | 15% | fineweb-edu |
| 中文教育 | 450M | 15% | opencsg/chinese-fineweb-edu |
| **code** | **450M** | **15%** | codeparrot-clean / python-edu |
| 合成教材 | 300M | 10% | cosmopedia-v2 |
| **tool** | **90M** | **3%** | API 文档 + schema 文本 |
| math | 60M | 2% | 保留少量，不做专家 |

## 6. 和路由的关系（重要）

上面的数据是**按来源成块**的，这对 MoE 专家分化有直接影响：

- 好的一面：同一批里领域一致，router 更容易学出稳定的专家分配；
- 坏的一面：如果**顺序**喂（先 general 后 code 最后 tool），会出现灾难性遗忘和
  router 在边界处的剧烈震荡；而且末尾 13.5 万条 tool 会变成一个"只学 tool"的收尾阶段。

**正确做法**：按领域分组 → 组内做成纯领域 batch → **打乱 batch 顺序**。
详见 `doc/moe_specialization.md` §3。
