# MoE 专家分化：数据怎么排、超参怎么调、怎么验证

> 对象：`mini_145m_a60m`（6 routed experts / top-2 / 2 层 hash routing / 7 层）。
> 回答三个问题：领域数据"集中出现"是否促进分化、`sft_t2t` 的块状结构意味着什么、
> 有哪些可操作的促进手段（含学习率计划）。
>
> 标注约定：**【实测】** 是本仓库跑出来的，**【经验】** 是社区/论文的普遍观察，
> **【建议】** 是本文主张、尚未在 145M 上验证。

---

## 1. 先给结论

1. **"集中"要发生在 batch 粒度，不是训练阶段粒度**。领域同质的 batch 促进分化；
   先训 100M token 通用再训 100M token 代码，只会得到遗忘 + router 震荡。
2. **平衡损失是分化的天敌**。它越强，专家越均匀，分化越弱。正确做法是
   「前期强平衡防塌缩，后期退火让分化长出来」。
3. **学习率不是分化手段**。warmup + cosine 是稳定性手段；早期 LR 过大反而加剧
   router 抖动、降低分化质量。想促进分化，改数据排布和平衡损失，不要改 LR。
4. **能不能分化，先看结构上限**：6 专家 top-2，最多同时 3 组；前 2 层 hash routing
   按 token id 固定分派、与领域无关，**真正可学的路由只有后 5 层**。别期待干净的
   "一个领域一个专家"。

---

## 2. "集中出现"为什么有用：机制

MoE 的 router 是 **per-token 决策**，但它的梯度来自 **per-batch 的统计**：
负载均衡损失、专家 bias 更新、以及同一 batch 内 token 的竞争，都是 batch 级的。

```text
混合 batch（general+code+tool 各 1/3）
  → 每步 router 被三股方向拉扯
  → 专家权重学成"平均专家"
  → 负载均匀，但没有分化

纯领域 batch（这一步全是 code）
  → router 更新方向一致
  → 同两个专家反复接 code token
  → 专家权重朝 code 偏移，路由模式稳定
```

这就是"领域 batching"有效的根本原因：不是数据本身特殊，而是**更新信号的同质性**。

**【经验】** Switch Transformer、DeepSeekMoE、OLMoE 的路由分析都观察到：不加任何领域标签，
专家也会自发按语法、语言、领域分化。也就是说分化是**自然发生**的，数据排布只是
"顺水推舟"或"逆水行舟"。

### 边界：集中 ≠ 顺序

| 做法 | 结果 |
|---|---|
| 纯领域 batch，batch 顺序打乱 | ✅ 分化好，且不遗忘 |
| 领域 A 训完再训 B（顺序块） | ❌ 灾难性遗忘；router 在边界处硬切换，泛化变差 |
| 全部混合 batch | ⚠️ 稳定但分化弱，专家趋同 |
| 纯领域 batch + 10–20% 混合 batch | ✅✅ 分化好且路由不过拟合（推荐） |

**为什么纯顺序不行**：Expert 权重是共享的，B 阶段会把 A 阶段学到的专家用法覆盖掉；
更糟的是 router 会学出一个"硬分块"策略（看到 B 的数据就整体切到另一组专家），
这个策略在真实推理时（输入是混合的）不成立。

## 3. 你现在的数据是什么结构【实测】

`minimind/dataset/sft_t2t.jsonl` 按位置采样：

| 位置 | 主导内容 |
|---|---|
| 0–33% | 通用 70–79% + 代码 17–28% |
| 41%、58%、66% | 通用 92–98% |
| 75% | 数学 22.8%（数学块） |
| **83%** | **代码 72.6%（大代码块）** |
| 91% | 通用 95% |
| 尾部 | tool 块（`sft_t2t_mini` 第 771,075–905,718 行，13.5 万条） |

`sft_t2t_mini.jsonl` 更极端：16% 处一个代码块（32.5%），末尾一整块 tool（100%）。

**这是按来源拼接的产物，不是设计。** 三种处理方式：

| 处理 | 后果 |
|---|---|
| 直接顺序读 | ❌ 末尾变成"只学 tool"的收尾阶段，通用能力回退 |
| 全局 shuffle（仓库当前做法） | ✅ 安全，但**丢掉了领域同质 batch 的分化收益** |
| 按领域分组 → 组内成 batch → 打乱 batch 顺序 | ✅✅ 本文推荐 |

仓库现状：`data/sft.py` 与 `data/pretrain.py` 在 tokenize 阶段 `rng.shuffle(indices)`，
所以现在是"全局 shuffle"。要拿到分化收益，需要改成"分组打包 + batch 级混料"。

**好消息**：`src/minideepseek/data/mix.py` 的 `WeightedBatchMixer` 已经是现成的积木——
把每个领域打成独立的 packed 数据集，各挂一个 `BatchSource`，权重就是目标配比，
它保证**每个 batch 只来自一个源**（天然纯领域），同时按比例混合、顺序可复现。

## 4. 促进分化的手段（按杠杆排序）

### 4.1 数据侧（杠杆最大）

| 手段 | 做法 | 代价 |
|---|---|---|
| **领域同质 batch** | 每域一个 packed 数据集 + `WeightedBatchMixer` | 需要按域重新打包 |
| **batch 顺序打乱** | mixer 已支持固定 seed 的 shuffle | 无 |
| **留 10–20% 混合 batch** | 加一个 `mixed` 源，权重 0.1–0.2 | 无 |
| **课程：通用打底 → 领域收尾** | 前 70% 步数 general 权重高，后 30% 提高到领域 | 需要改权重调度 |
| **不要在样本级混** | 一个 4K pack 里塞三种领域 = 自我拆台 | 无 |

课程的正确形态（不是顺序块）：

```text
step    0 ─────────── 70% ─────────── 100%
general  ████████████████████████░░░░░░   55% → 35%
code     ██████░░░░░░░░░░░░░░░░░░░░░░░   20% → 35%
tool     ██░░░░░░░░░░░░░░░░░░░░░░░░░░░    5% → 15%
mixed    ████░░░░░░░░░░░░░░░░░░░░░░░░░   20% → 15%
```

### 4.2 路由侧

| 手段 | 现在 | 建议 |
|---|---|---|
| 序列级平衡损失 `balance_loss_coeff` | `1e-4` 固定 | **退火**：前 50% 保持 1e-4，后 50% 线性降到 1e-5 甚至 0 |
| loss-free bias `load_balance_coeff` | `1e-3` | 保持小值；这是 V3/V4 的设计，专为"不牺牲分化地保平衡" |
| hash 层 `n_hash_layers` | 2 | 保持；前 2 层 hash 把可学习容量留给后 5 层，合理 |
| router 噪声/jitter | 无 | 前 10–20% 步数加小噪声帮助探索，之后关掉 |
| 路由归一化 `route_norm` / `route_scale` | true / 1.5 | 不动 |

**为什么平衡损失要退火**：均衡损失的作用是防止"所有 token 挤 2 个专家"，但它同时
惩罚"某些专家被某领域专用"。前期需要它防塌缩，后期需要撤掉它让分化定型。
一直固定 1e-4，等于一直在给分化踩刹车。

### 4.3 优化侧（含学习率）

**先纠正一个说法**：学习率"一开始大后面减小"是 warmup + cosine 的标准形态，
它的目标是**稳定训练**，不是促进分化。对 MoE 来说，早期 LR 过大反而有害：
router 的 softmax 在高温区抖动，专家分配每步都在换，专家权重学不到稳定模式。

**【建议】145M 的具体计划**：

| 项 | 值 | 理由 |
|---|---|---|
| warmup | 300–500 step | 让 router 先找到大致分配再加速 |
| peak LR | 6e-4（现有配置） | 145M 的常用量级；若看到 expert load 曲线剧烈震荡，降到 3–4e-4 |
| decay | cosine → 10% | 现有配置，合理 |
| router/embedding 参数 | AdamW 组，LR × 0.5–1.0 | router 比矩阵更敏感；震荡时先降 router |
| grad clip | 1.0 | 现有配置，保持 |
| 平衡损失退火 | 见 4.2 | 比调 LR 有效得多 |

**判断标准**：看 `domain_*_expert_load_max_over_mean` 的曲线。若它在训练中来回跳，
说明 router 不稳（降 LR / 加 warmup）；若它一直贴近 1.0，说明分化没起来（退火平衡损失）。

### 4.4 结构侧（本阶段不建议动）

- 专家数 6 → 8/12 会提升分化上限，但 145M 下每个专家会更小，单专家容量不足；
- top-2 → top-1 强制更硬的分派，分化更明显但质量下降；
- 这两项属于"结构实验"，不是数据阶段该做的事。

## 5. 怎么验证分化（不要靠感觉）

仓库已有 `model/routing.py::domain_routing_metrics`，按 domain 输出：

| 指标 | 含义 | 期望 |
|---|---|---|
| `domain_{d}_expert_load_max_over_mean` | 该领域最热专家 / 平均负载 | **> 1.5** 说明有集中；≈1 说明没分化 |
| `domain_{d}_routing_entropy_normalized` | 路由熵（归一化） | 参考值 0.5–0.8（需在 145M 上标定）；**< 0.3 基本是塌缩** |
| `domain_{d}_experts_used_fraction` | 该领域用到多少专家 | code/tool 3–4/6 合理；=1/6 是塌缩 |

**关键判据不是"越集中越好"**，而是：

```text
不同领域的 expert_load 向量要"不同"（分化）
每个领域的 routing_entropy 不能太低（不塌缩）
```

也就是看**领域间**的差异，而不是单领域的集中度。可以进一步算领域间专家分布的
JS 散度，只作为**趋势指标**看它是否随训练上升；具体阈值要在 145M 上先跑 2–3 个
短 run 标定，本文不给硬数字（避免拿经验值当结论）。

---

## 6. 落地顺序

1. 先把每个领域打成独立的 packed 数据集（`data/tokenized/{general,code,tool}_*.npz`）；
2. 用 `WeightedBatchMixer` 按 §4.1 的配比混 batch，验证每个 batch 只来自一个领域；
3. 打开 `domain_routing_metrics`，在 debug 模型上先看指标能出数；
4. 加平衡损失退火（这是唯一需要改训练循环的地方）；
5. 在 145M 上跑 2–3 个短 run（各 200M token）对比：固定平衡 vs 退火、纯混合 vs 领域 batch。

---

## 7. 不要做的事

- ❌ 按文件顺序训练（tool 块在末尾 = 最后只学 tool）；
- ❌ 把 `balance_loss_coeff` 调大来"稳定训练"（会抹平分化）；
- ❌ 为了分化把 LR 调大（只会让 router 抖）；
- ❌ 把 domain label 喂给 router（推理时拿不到 label，会退化成硬规则）；
- ❌ 用单领域的集中度当唯一指标（塌缩也会让这个数很高）。
